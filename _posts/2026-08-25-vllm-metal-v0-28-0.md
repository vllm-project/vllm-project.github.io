Local inference on a Mac is straightforward until several requests overlap. Then time to first token (TTFT), memory growth, and admission control become serving problems rather than model-execution problems. [vllm-metal](https://github.com/vllm-project/vllm-metal) brings vLLM's scheduler, paged KV cache, and OpenAI-compatible server to Apple Silicon, with MLX and Metal handling execution.

v0.28.0 adds batched multi-token prediction (MTP), GGUF and hybrid-model support, and faster prefill on M5.

## How vllm-metal fits into vLLM

vllm-metal plugs into upstream vLLM. vLLM provides the V1 scheduler, paged KV block management, chunked prefill, sampling, and the OpenAI-compatible frontend with streaming and tool-call parsing. mlx_lm provides the model implementations; MLX executes them.

At the model level, vllm-metal reuses mlx_lm's weight loading, RMSNorm, linear, MoE, and MLP layers unchanged. Those layers process each token independently, so they run on a packed token axis without knowing request boundaries. Attention does need those boundaries, so vllm-metal replaces stock attention with a paged varlen Metal kernel. Most of the plugin's model-specific code therefore sits in one layer.

![Architecture overview: clients speak the OpenAI API to upstream vLLM's frontend and V1 scheduler, which hand the vllm-metal model runner a packed step plus block tables; the runner reuses mlx_lm's token-wise layers and adds custom Metal paths for paged varlen attention, MTP, and M5 NAX prefill, all executing through MLX and Metal on Apple Silicon unified memory](/assets/figures/2026-08-25-vllm-metal-v0-4-0/arch.svg)

## Start an OpenAI-compatible server

Install vllm-metal into its own virtual environment and activate it:

```bash
curl -fsSL https://raw.githubusercontent.com/vllm-project/vllm-metal/main/install.sh | bash
source ~/.venv-vllm-metal/bin/activate
```

The installer adds the plugin, vLLM core, and their dependencies to `~/.venv-vllm-metal`.

Then launch a model:

```bash
# --gpu-memory-utilization sets the serving memory budget; see below.
vllm serve Qwen/Qwen3.5-0.8B --gpu-memory-utilization 0.5

# 64 GB Macs: the 27B hybrid
# vllm serve mlx-community/Qwen3.8-27B-4bit --gpu-memory-utilization 0.7

# Speculative decoding: Gemma 4 with its MTP assistant
# vllm serve google/gemma-4-E4B-it --gpu-memory-utilization 0.5 \
#   --max-model-len 16384 --no-async-scheduling \
#   --speculative-config '{"method":"mtp","model":"mlx-community/gemma-4-E4B-it-assistant-bf16","num_speculative_tokens":1}'
```

More models: [model matrix](https://github.com/vllm-project/vllm-metal/blob/main/docs/supported_models.md).

The server speaks the OpenAI API:

```bash
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "Qwen/Qwen3.5-0.8B",
       "messages": [{"role": "user", "content": "Say hi"}]}'
```

Anything that takes an OpenAI-compatible base URL can point at `http://localhost:8000/v1`, coding agents included; the vLLM docs cover [Claude Code](https://docs.vllm.ai/en/latest/serving/integrations/claude_code/) and [Codex](https://docs.vllm.ai/en/latest/serving/integrations/codex/) setup.

## Set a predictable memory budget

vllm-metal's memory guard lets you set an inference budget with `--gpu-memory-utilization`, leaving headroom for macOS and your apps. Like upstream vLLM, it runs a warmup pass at startup to account for model weights, activations, and temporary buffers before allocating the remaining budget to a fixed KV cache. It also caps MLX's reusable buffer cache to prevent memory from accumulating during serving. Requests that do not fit in the KV pool wait until pages become available.

## Packed queries and paged KV

In mlx_lm's padded batches, attention queries have shape `[B, H, T_max, D]`: every request gets the longest query length in the batch. MLX's `scaled_dot_product_attention` has no varlen interface.

vllm-metal preserves vLLM V1's unified model step for chunked prefill and decode. It packs every scheduled query token into `[total_q, H, D]`, with `cu_seqlens` marking request boundaries, and runs the mixed step in one model forward.

KV is separate: mlx_lm keeps a contiguous `[B, H, T, D]` cache, while vllm-metal stores KV in fixed-size pages addressed by per-request block tables. Admitted requests can grow without reshaping a padded cache.

The engines in this comparison handle prefill batching differently:

| Engine | Prefill batching | Query axes | KV |
|---|---|---|---|
| mlx_lm | padded, up to 8 prompts | `[B, T_max]` | contiguous |
| oMLX | one prompt at a time | `[1, T]` | contiguous |
| llama.cpp | mask over slots | `[total_q]` | fixed cells |
| vllm-metal | packed, `cu_seqlens` | `[total_q]` | paged |

![A padded rectangle versus vllm-metal's packed varlen step for a 4,000 + 1,000 + 1,000 token batch, with KV read from paged storage](/assets/figures/2026-08-25-vllm-metal-v0-4-0/kv-layout.svg)

On Qwen3.6-35B-A3B in 4-bit, we compared batches of eight requests with roughly 6,000 prompt tokens in total and 20 output tokens per request. Batch A has similar prompt lengths; batch B has one longer prompt. The table reports batch wall time in seconds, with prompt lengths rounded.

| Batch | Prompt tokens | mlx_lm | oMLX | llama.cpp | vllm-metal |
|---|---|---:|---:|---:|---:|
| A | 750 × 8 | 4.52 | 7.32 | 5.29 | 3.87 |
| B | 3,000 + 430 × 7 | 10.99 | 7.22 | 5.33 | 3.64 |
| **Change** | | **+143%** | −1% | +1% | −6% |

Packing also keeps ragged work in one batch. In a speculative step, one request may contribute a single decode token, another its last token plus a request-specific number of drafts, and another a prefill chunk. A `[B, H, T_max, D]` query tensor must either pad those rows to a common width or split them across forwards. vllm-metal instead concatenates the windows as `[total_q, H, D]` and verifies them in one target-model forward.

The Metal kernel ports vLLM's unified Triton kernel, described in [*The Anatomy of a Triton Attention Kernel*](https://arxiv.org/abs/2511.11581), to Apple GPUs, down to the binary search each threadgroup runs over `cu_seqlens` to find which request owns its query token.

## Concurrent serving under agent load

Multiple coding agents or sessions can send model requests at the same time. We measured this with [SiliconBench](https://github.com/WindChimeRan/SiliconBench)'s agent split: 100 multi-turn prompts with roughly 4.6K input tokens each, on an M5 Pro with 64 GB of memory. All three model comparisons use 4-bit weights.

Each concurrency level starts with a fresh server. oMLX is shown with its default SSD cache and with a RAM-only cache; both start empty. The [appendix](#appendix-benchmark-reproduction) gives the serving configurations, and the figure captions report completion counts.

### Qwen3.8-27B

![SiliconBench agent split on Qwen3.8-27B: TTFT, end-to-end request latency, and output token throughput versus concurrency for llama.cpp, vllm-metal, and oMLX with its prefix cache in memory and on SSD](/assets/figures/2026-08-25-vllm-metal-v0-4-0/siliconbench-27b.svg)

vllm-metal has the lowest TTFT and end-to-end latency at concurrency 2 and 4. oMLX with SSD offload leads at concurrency 1.

### Gemma 4 E4B

For Gemma 4 E4B, we extend the sweep to concurrency 16 and include vllm-metal with its MTP drafter.

![SiliconBench agent split on Gemma 4 E4B: TTFT, end-to-end request latency, and output token throughput versus concurrency for llama.cpp, vllm-metal with and without the MTP drafter, and oMLX with its prefix cache in memory and on SSD](/assets/figures/2026-08-25-vllm-metal-v0-4-0/gemma-e4b.svg)

vllm-metal keeps TTFT low throughout this sweep. llama.cpp uses its default four server slots; a separate BF16 [slot-sensitivity experiment](#llamacpp-server-slot-sensitivity) is included in the appendix.

### Qwen3.6-35B-A3B

Qwen3.6-35B-A3B has 35B total parameters with 3B active per token. It combines mixture-of-experts layers with standard attention and gated-delta-net (GDN) linear attention.

![SiliconBench agent split on Qwen3.6-35B-A3B: TTFT, end-to-end request latency, and output token throughput versus concurrency for llama.cpp, vllm-metal, oMLX with its prefix cache in memory and on SSD, and mlx_lm](/assets/figures/2026-08-25-vllm-metal-v0-4-0/moe-35b-a3b.svg)

At concurrency 4, vllm-metal and oMLX with a RAM cache are close in throughput and end-to-end latency, with a larger gap in TTFT. mlx_lm's line covers only the minority of requests it completed.

### Batched MTP under concurrent load

MTP uses an assistant model to draft tokens, which the target model verifies within the continuous batch. The table compares one draft token per step with generation without MTP on Gemma 4 E4B:

| Concurrency | Wall vs. no MTP | Output tok/s vs. no MTP | TTFT avg vs. no MTP |
|---:|---:|---:|---:|
| 1 | −15% | +20% | −1% |
| 8 | −1% | +0% | +4% |
| 16 | −8% | +9% | +20% |

MTP is opt-in through `--speculative-config`. The Metal path currently supports Gemma 4 with plain greedy sampling (`temperature=0`) and synchronous scheduling (`--no-async-scheduling`).

## Other v0.28.0 additions

### Faster prefill on M5

On M5 Macs, vllm-metal automatically uses the NAX attention kernel, which uses the GPU's tensor hardware, for compatible prefill batches. Earlier Macs keep using the existing path. This comparison uses Qwen3-0.6B:

![NAX versus tiled attention on Qwen3-0.6B: time to first token, total token throughput, and time per output token](/assets/figures/2026-08-25-vllm-metal-v0-4-0/nax-prefill-ab.png)

### Reusing conversation history on hybrid models

Multi-turn agents resend most of their growing conversation on every turn. Prefix caching lets the next turn reuse blocks computed for earlier turns instead of prefilling the full history again.

For Qwen3.5-style hybrid models, vllm-metal supports vLLM's `align` mode. It saves GDN recurrent state at the same block boundaries as attention KV, allowing both to resume from a cached prefix ([PR #634](https://github.com/vllm-project/vllm-metal/pull/634)). This path remains experimental and cannot yet be combined with speculative decoding.

### Models and serving features

v0.28.0 also ships:

- LoRA adapters, structured outputs, and three speculative-decoding methods: Gemma 4 MTP, separate draft models, and prompt-lookup n-grams.
- GGUF checkpoints, including Hugging Face config sources for local GGUF weights.
- Hybrid-attention models from the Qwen3.5, Qwen3.6, Qwen3.8, and Qwen3-Next families.
- Pipeline parallelism across multiple Macs over the MLX ring backend.
- Experimental vision-language models, text embeddings and reranking, and speech-to-text.

The supported-model matrix and feature guides are in the [vllm-metal documentation](https://docs.vllm.ai/projects/vllm-metal/en/latest/).

## Appendix: benchmark reproduction

The cross-engine serving benchmarks use the SiliconBench agent split, run closed loop at fixed concurrency on a 64 GB M5 Pro, with greedy sampling. Stats cover completed requests; an empty response counts as failed. Each engine uses its own 4-bit model conversion. For Qwen3.8-27B, the MLX conversion has 15.0 GiB of text weights and llama.cpp's `UD-Q4_K_M` has 15.3 GiB.

Each concurrency level gets a fresh server and, for oMLX, a fresh cache directory. The oMLX SSD configuration uses a 100 GB disk cache with its memory tier off; the RAM configuration uses an 8 GB memory cache with disk writes off. vllm-metal uses its default memory fraction, `auto`, which resolves to `--gpu-memory-utilization 0.92`; oMLX uses its balanced memory guard; llama.cpp has no explicit memory cap. The quickstart uses a lower memory budget to leave room for other applications.

The padding comparison reports the median of two runs per cell, with a fresh server for each run. Each run sends eight requests with 20 output tokens each. The NAX A/B uses Qwen3-0.6B with two Sonnet configurations: 2,048 input / 32 output tokens and 1,024 input / 128 output tokens. Both run 100 prompts at request rate 10 and concurrency 32.

The cross-engine benchmark code, configurations, and result files live in the [SiliconBench repo](https://github.com/WindChimeRan/SiliconBench). Those comparisons use vllm-metal `0.28.0.dev20260901062632` with vLLM 0.28.0, llama.cpp `0eadefeb`, and oMLX `dc312e6e`.
