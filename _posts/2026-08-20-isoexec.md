## TL;DR

In theory, on-policy RL assumes that rollout and training evaluate the same policy. In practice, RL training systems often use two separate engines for rollout and training, with different model definitions, kernels, batch shapes, and parallelism layouts. Because floating-point arithmetic is non-associative, those differences can change token probabilities even when executing the same policy. This can make new RL algorithms, changes in harnesses and environments, and improvements to RL infrastructure and hardware kernels hard to debug.

To resolve this problem, we introduce **IsoExec**, a cross-framework numerical execution abstraction for eliminating mismatch between the training and inference engines for RL workloads. IsoExec captures model execution details that can affect floating-point rounding order (for example, reduction order) in an execution contract, then enforces that contract so the underlying systems execute a unified numerical policy. We implement IsoExec on SkyRL with vLLM and Megatron. On a single H100 node, with synchronous Qwen3.5-35B-A3B DAPO training, we achieve **zero train–inference engine mismatch** with only 25% overhead compared with the current SkyRL baseline, tested over 50 steps.

Our main contributions are:

- **Unified execution abstraction:** One numerical execution contract across training and inference, enabling zero mismatch with minimal overhead and low debugging cost for new RL algorithms, changes to RL environments and harnesses, and kernel improvements.
- **Parallelism-invariant kernels:** Preserve numerics across tensor, expert, and sequence parallelism.
- **Chunkwise-parallel recurrent (CPR) Gated DeltaNet:** Aligns training, prefill, and recurrent decode without serializing long-sequence forward passes.

## Introduction

RL workloads require executing the same policy twice to generate rollouts (rollout engine) and train the policy (trainer). The rollout engine samples a token with log probability $\mu$; the trainer later recomputes $\pi$ for that token using the same model parameters (synchronous RL). Typical on-policy RL assumes $\mu = \pi$ (i.e., no training–inference mismatch). From a systems perspective, true on-policy training is hard due to floating-point non-associativity:

$$
(a+b)+c \neq a+(b+c).
$$

RL systems often use existing inference systems such as vLLM and SGLang alongside training systems such as Megatron and FSDP. These systems are optimized for different tasks, including kernels, batch shapes, training, prefill, decode, and distributed layouts. As a result, they can use different reduction orders when executing the same mathematical model, leading to different output token probability distributions.

ByteDance's [VeXact study](https://arxiv.org/abs/2605.14220) shows that mismatch alone can collapse REINFORCE and GRPO runs, distort advantage-weighted loss contributions before a KL estimator reacts, and make importance-sampling or rejection-based fixes sensitive to calibration. [Fireworks](https://fireworks.ai/blog/frontier-lab-training-infrastructure-as-a-service) reports a GLM-5.2 run with train–inference KL around 0.013 where clipping discarded roughly 45% of tokens and reward collapsed around step 20, while a bitwise-aligned run had zero clipped tokens and remained stable.

Previous work on system determinism has focused on parts of the problem. [Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) formalized batch invariance: a token's result should not depend on what else shares its batch. The [vLLM × TorchTitan](https://vllm.ai/blog/2025-11-10-bitwise-consistent-train-inference) bitwise-consistency work showed that importing matched kernels into both engines can reach parity, but still requires two aligned model copies. More recent work on [Zero Train–Inference Mismatch for Linear Attention and Async RL](https://yichuan-w.github.io/blog/GDN-train-inference-mismatch-asyncRL/) shared one model definition between the TorchTitan trainer and vLLM generator and extended parity to [Gated DeltaNet](https://arxiv.org/pdf/2412.06464), using the recurrent forward path everywhere while retaining the chunked kernel for backward. [Tree-Based Invariant Kernels (TBIK)](https://arxiv.org/abs/2511.17826) (Zhang et al., ICML 2026) focused on achieving bitwise consistency under different parallelism configurations.

IsoExec targets train–inference mismatch at the numerical execution layer. Rather than requiring training and inference to use identical framework code or kernels, IsoExec defines a framework-independent numerical contract and lowers it into each runtime while preserving its semantics. The contract specifies the implementation, dtypes, reduction order, and other execution choices that affect floating-point results. This lets the training and inference engines retain their native training and serving designs while executing the same model with the same numerical semantics.

## Unified execution abstraction

IsoExec enforces unified execution across training and rollout engines with an **execution contract**.

```
{
  "ExecutionContract": {
    "cases": [ ... ],        // the logprob computations: trainer_fwd, engine_decode, ...
    "composition": [ ... ],  // (region, case) -> implementation + pinned constants
    "claims": { ... },       // topology invariance, state invalidation, tolerances
    "identities": { ... }    // semantic / numerical_policy / deployment digests
  }
}

```

The contract handles each computation of a token's logprob by **case** (e.g. rollout `engine_prefill` and trainer `trainer_fwd`). The model's forward operators are partitioned into **regions**, groups of arithmetic implemented by one kernel (which may contain fused operators). For every (region, case) pair, the **composition** selects the implementation and the constants it is pinned to. The constants are anything that can change the bits, such as accumulation dtype, boundary dtype, and kernel tile sizes. Every op region is tested for bitwise exactness across the cases before its implementations may be registered into the composition.

Example:

```
"composition": [
  {
    "region": ["gdn.core", "gdn.gating", "norms.l2"],
    "cases": ["trainer_fwd", "trainer_score", "engine_prefill", "engine_decode"],
    "impl": {"id": "native_fused_sigmoid", "version": 1, "arch": "sm90"}
  },
  {
    "region": ["moe.combine"],
    "cases": ["engine_prefill", "engine_decode"],       // the trainer side is its own entry
    "impl": {"id": "pik_leaf_tree", "version": 2, "arch": "sm90"},
    "constants": {"leaves": 8, "leaf_dtype": "fp32"},   // constants change bits, so they are identity
    "discharge": {"kind": "equivalence_proof", "ref": "gates/ep_invariant_combine"}
  }
]
```

**Claims** state the conditions the composition's guarantees hold under. For example, the parallelism-invariant reduction trees are proven only for the declared TP sizes, and the cached state must be invalidated after weight sync.

The **identities** are sha256 encodings of the serialized contract, used to enforce contract agreement in trainer and rollout engines. `semantic` asserts whether runtimes describe the same logical model, `numerical_policy` covers everything that can change execution (e.g. implementations, versions), and `deployment` covers settings proven not to affect the bits, such as memory sizing and transport configuration, which the contract will not enforce. Since every implementation entered the composition through the pre-registration bitwise tests, matching hashes indicate both sides are running the same already-verified numerics.

The execution contract is installed to every trainer/engine process via the **contract adapter**, enabling multiple backends to enforce the contract. For the SkyRL system, we adapt a unified model definition based on Megatron's `GPTModel`, but integrate it with vLLM's engine features (e.g. scheduler, KC cache manager, piecewise CUDA graphs). The implementation of IsoExec can be found [here](https://github.com/zanderjiang/SkyRL-IsoExec).

![IsoExec's unified execution contract across training and inference runtimes.](/assets/figures/2026-08-20-isoexec/unified_execution_abstraction.png)

For experiments, we applied the abstraction to achieve zero-mismatch training on dense (MiMo-7B), MLA MoE (GLM-4.7-Flash), hybrid (Qwen3.5-9B), and hybrid MoE (Qwen3.5-35B-A3B) models.

## Parallelism-invariant kernels

Ideally, training and inference use different distributed strategies. The trainer must fit optimizer state, activations, gradients, and, for MoE models, distributed expert weights. The rollout engine instead needs enough memory capacity for the KV cache without hurting decode latency.

Of the six common parallelism axes:

- **Data parallelism (DP)** only changes batch partitioning, which batch invariance already handles.
- **Pipeline parallelism (PP)** moves whole layers across devices without splitting their reductions.
- **Tensor parallelism (TP)** splits contraction reductions across ranks.
- **Expert parallelism (EP)** distributes expert computation and changes how expert outputs are combined.
- **Sequence parallelism (SP)** changes row-parallel reductions from all-reduce to reduce-scatter.
- **Context parallelism (CP)** splits the attention reduction across the sequence dimension.

[TBIK](https://arxiv.org/abs/2511.17826) (Zhang et al., ICML 2026) achieved TP-invariant inference by fixing a global reduction tree across row-parallel GEMMs and the cross-GPU reduction. IsoExec takes the same fixed-reduction idea but applies it along the K dimension. Instead of building the tree over GEMM K-tiles, `pik` divides the K dimension into $G$ contiguous leaves. Each leaf uses the GPU's Tensor Core deterministic FP32 MMA accumulation. The partial results are then combined with NCCL, instead of custom communication kernels, in a fixed binary reduction tree.

![The fixed binary reduction tree used by pik to preserve numerics across parallelism layouts.](/assets/figures/2026-08-20-isoexec/pik_figure.png)

IsoExec also applies the same principle to EP and SP. For expert parallelism, we combine expert outputs in a fixed routing order rather than rank order. For sequence parallelism, we reuse the same reduction tree as the non-SP system; each rank keeps its own output slice instead of gathering the full result. This makes SP-on and SP-off trainer logits bitwise identical at TP2 and TP4.

On a Megatron `RowParallelLinear` at TP8:

| Stage | Shape ($M$) | Megatron `RowParallelLinear` | TBIK | `pik` (ours) |
|--------|-------|----------------------------------|------|---------------|
| Bitwise exact | — | No | Yes | **Yes** |
| Decode | 256 | 0.2196 ms | 0.3236 ms (1.47×) | **0.3180 ms (1.45×)** |
| Trainer microbatch | 1,536 | 0.2682 ms | 0.6616 ms (2.47×) | **0.4245 ms (1.58×)** |
| Prefill | 8,192 | 0.3748 ms | 2.6301 ms (7.02×) | **0.7044 ms (1.88×)** |

*Forward latency per layer for `o_proj` ($K=4096$, $N=2048$) on 8×H100 at TP8. Ratios are relative to the native Megatron path; smaller is better.*

## Chunkwise-parallel recurrent (CPR) GDN

Linear attention architectures are more complex because training and inference use completely different algorithms. GDN trains and prefills with a chunkwise-parallel form, but decodes in recurrent form. Although mathematically identical, the algorithms have different floating-point rounding characteristics. In existing implementations—[FLA's](https://github.com/fla-org/flash-linear-attention) chunkwise-parallel kernel and vLLM's fused recurrent kernel—we observe mean decode–prefill differences around $1.7 \times 10^{-2}$, with a maximum difference of 0.25.

[TorchTitan](https://yichuan-w.github.io/blog/GDN-train-inference-mismatch-asyncRL/) addressed this issue by using the recurrent form for both prefill and training forward computation, and using the chunkwise form only for backward computation. Although this removes mismatch for GDN, it makes trainer forward and prefill sequential in sequence length. The authors report a slowdown of roughly 2–3× on math workloads and about 5× on a terminal-agent workload, making the approach impractical for our use case.

To ensure zero mismatch while achieving high throughput for both prefill/training and decode, we designed **chunkwise-parallel recurrent (CPR)**. CPR keeps the recurrence as the main function but evaluates it in parallel across chunks. For training and prefill, similar to the chunkwise-parallel form, a first pass computes the recurrent state at every chunk boundary; a parallel recurrent scan then computes the outputs within each chunk. For decode, we use the recurrent form, but resynchronize the hidden state after every chunk-size group of decoded tokens. This ensures a consistent rounding schedule across prefill, training, and decode.

Per-layer cost:

| Stage | Shape | Native mixed | Chunkwise everywhere | Recurrent everywhere | CPR |
|-------|-------|--------------|----------------------|----------------------|-----|
| Bitwise exact | — | No | Yes | Yes | **Yes** |
| Trainer forward + backward | 1 × 10,240 tokens | 5.177 ms | 5.177 ms (1.00×) | 22.863 ms (4.42×) | **7.386 ms (1.43×)** |
| Rollout-engine prefill | 5 × 2,048 tokens | 0.844 ms | 0.844 ms (1.00×) | 3.639 ms (4.31×) | **1.412 ms (1.67×)** |
| Rollout-engine decode | 256 sequences × 1 token | 0.0612 ms | 2.2374 ms (36.6×) | 0.0612 ms (1.00×) | **0.0846 ms (1.38×)** |

*Per-layer latency on H100 ($C=64$). The trainer and engine use the production TP layouts and kernels. Ratios are relative to the native Megatron path; smaller is better.*

## Results

For our experiments, we compare IsoExec against SkyRL's native stack on an 8×H100 node by training **Qwen3.5-35B-A3B** on the DAPO 17K AIME dataset with synchronous RL. With identical setups, IsoExec has 25% overhead compared with the native SkyRL stack using vLLM and Megatron backends under the most optimized synchronous-RL throughput configuration.

![Rollout-versus-training absolute logprob differences for the native SkyRL stack and IsoExec.](/assets/figures/2026-08-20-isoexec/result_logprob_diff.png)

Across 50 steps, the pre-update rollout-versus-training absolute logprob difference falls from **$1.648 \times 10^{-2}$** to **$6.744 \times 10^{-7}$** in mean, from **$4.035 \times 10^{-2}$** to **$6.821 \times 10^{-7}$** in standard deviation, and from **5.073** to **$7.358 \times 10^{-6}$** for the average per-step maximum.

![Average RL step timing for the native SkyRL stack and IsoExec over 50 steps.](/assets/figures/2026-08-20-isoexec/result_time.png)

For performance, we compare the average step time over a 50-step window and observe 25% end-to-end overhead.

| Metric | Native | IsoExec | Overhead |
|--------|--------|---------|----------|
| Generation | 591.3 s | 776.6 s | **31.3%** |
| Policy training | 498.6 s | 591.3 s | **18.6%** |
| Full RL step | 1224.6 s | 1534.0 s | **25.3%** |

### Training outcomes

![Pass@16 and raw reward for the native SkyRL stack and IsoExec over 50 steps.](/assets/figures/2026-08-20-isoexec/result_reward.png)

Over a short 50-step run, we do not observe a statistically significant improvement from zero train–inference mismatch over the baseline. Mean pass@16 increases from 0.873 to 0.876, while mean raw reward increases from 0.144 to 0.148.
