### Introduction

As vLLM becomes a leading standard for LLM serving, a key requirement for hardware vendors is deep integration with the vLLM execution model—without disrupting its developer experience.

At Qualcomm Technologies, this is achieved through a plugin-based backend implementation (vllm-qaic) that enables seamless execution on [Qualcomm Cloud AI](https://www.qualcomm.com/data-center/products/cloud-ai-100-ultra) and [Qualcomm Dragonfly AI](https://www.qualcomm.com/data-center/expertise/ai-accelerators) accelerator products.

This approach allows reuse of vLLM APIs, hardware-specific optimizations, and rapid feature enablement.

### Why a Plugin-Based Backend?

The [vllm-qaic](https://github.com/qualcomm/vllm-qaic) repository defines this as a unified backend extension enabling integration with our AI accelerators using PyTorch and compiler stack.

### Architecture Overview

The architecture enables applications to interact with our AI accelerators through the standard OpenAI-compatible vLLM interface, with the vllm-qaic backend plugin handling model compilation, KV cache management, and hardware execution.

### Execution Flow Diagram

The plugin supports two execution modes, enabling flexibility between optimized static compilation and dynamic PyTorch-based inference

#### AoT mode: Single graph execution mode

In AoT mode, the Hugging Face model is first passed through QEfficient (Qualcomm Technologies' efficient transformers library), which applies model transformations—such as graph restructuring and operator substitutions—to make the model execute efficiently on Qualcomm Technologies' Glow compiler. QEfficient also annotates the exported graph with additional metadata that guides Glow in implementing tiling and multi-device parallelism strategies across the accelerator's SoCs.

Based on this tile assignment, Glow inserts communication primitives directly into the compiled graph, including the inter-chip communication required when a tile's inputs or outputs span multiple SoCs—handled through a dedicated communication library invoked by the compiled graph rather than through framework-level collective calls. Because Glow has full visibility into the graph, tiling plan, and chip topology at compile time, it can schedule both intra-chip and inter-chip communication to overlap with computation, hiding much of this latency behind compute.

The full model is represented and compiled as a single, unified graph—rather than being split into subgraphs—allowing Glow to optimize placement, tiling, and communication scheduling (including across chip boundaries) across the entire model at once. The result is a QPC (Qualcomm Program Container) binary that the AoT runtime loads directly for execution on the accelerator, avoiding any Python-level tracing or recompilation overhead at serving time.

#### JIT execution mode

JIT execution mode is the contemporary execution mode aligned with how vLLM supports other hardware backends—relying heavily on PyTorch, where the JIT runtime executes ATEN Ops, fused kernels or subgraphs compiled by the torch infrastructure itself, rather than a single ahead-of-time compiled artifact. Operators are dispatched via torch-qaic, with the option to leverage torch.compile and TorchInductor to trace, fuse, and generate optimized kernels—including Triton-based kernels—on the fly.

Multi-device and inter-chip communication in this mode is handled by QCCL (Qualcomm Collective Communication Library), a standalone library similar in role to other collective communication libraries. Because communication here is issued through discrete collective calls at the framework level rather than being scheduled by a whole-graph compiler with topology awareness, the scope for hiding these communication primitives—both intra-chip and inter-chip—behind computation is limited compared to AoT mode. This, combined with torch.compile's division of the model into multiple subgraphs compiled and executed separately on the JIT runtime, trades away some of the AoT path's cross-graph optimization opportunities in exchange for greater flexibility with dynamic shapes and control flow.

### Supported vLLM Features

- MXFP6 quantization
- MXINT8 KV cache
- Speculative decoding
- Guided decoding
- Tool calling
- LoRA serving
- Multimodal inference

Two cross-cutting references round out the feature set: the [vLLM arguments for QAIC](https://quic.github.io/cloud-ai-sdk-pages/1.21/Getting-Started/Model-Serving/vLLM-Serving/input-args-env-variables.html) page documents the Qualcomm Cloud AI–specific flags and environment variables, and the [Cross-Feature Support Matrix](https://qualcomm.github.io/vllm-qaic/user_guide/features/) shows which features can be combined. The recurring theme is that none of these require leaving the standard vLLM interface—quantization and KV-cache dtype, for example, are selected with ordinary command-line flags such as `--quantization mxfp6` and `--kv-cache-dtype mxint8`.

### Quick Start: Your First Model in Two Commands

For a single-node deployment, the standard pre-built container is all you need. Start an OpenAI-compatible server with a small model to confirm the stack end-to-end:

```bash
$ docker run --rm -it --network host \
    --device /dev/accel/ \
    --shm-size=4gb \
    ghcr.io/quic/cloud_ai_inference_vllm:1.22.0.0 \
    --host 127.0.0.1 \
    --port 8000 \
    --model Qwen/Qwen2-7B-Instruct \
    --max-model-len 8192 \
    --max-num-seqs 16 \
    --quantization mxfp6 \
    --kv-cache-dtype mxint8 \
    --additional_config='{
      "device_group": [0, 1]
    }'
```

Once the server is up, send a chat request to the OpenAI-compatible endpoint:

```bash
$ curl http://127.0.0.1:8000/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d '{
        "model": "Qwen/Qwen2-7B-Instruct",
        "messages": [
            { "role": "system", "content": "You are a helpful assistant." },
            { "role": "user", "content": "Explain vLLM in one sentence." }
        ],
        "temperature": 0.7,
        "max_tokens": 128
    }'
```

### The Takeaway

Our approach to vLLM integration is rooted in a simple principle: keep the serving interface unchanged, and innovate at the backend.

With [Qualcomm Cloud AI 100 Ultra](https://www.qualcomm.com/data-center/products/cloud-ai-100-ultra), we introduce a plugin-based backend architecture (vllm-qaic) that cleanly integrates our AI accelerators into the vLLM ecosystem—preserving APIs, workflows, and developer familiarity while enabling hardware-specific optimizations under the hood.

The same plugin-based model that enables AI 100 Ultra today is designed to carry forward across future generations of Qualcomm Dragonfly AI accelerators—[AI200](https://www.qualcomm.com/data-center/products/qualcomm-dragonfly-ai200), [AI250](https://www.qualcomm.com/data-center/products/qualcomm-dragonfly-ai250), [AI300](https://www.qualcomm.com/data-center/products/qualcomm-dragonfly-ai300), and beyond—enabling:

- Continuity for developers: no rewrite as hardware evolves
- Rapid adoption of new silicon capabilities within existing vLLM workflows
- Sustained alignment with the upstream vLLM ecosystem
