Sparse attention speeds up video generation by reducing attention computation. On PCIe-connected GPUs, however, much of the communication remains. GPUs finish computing sooner but still wait for remote data, making communication the new bottleneck.

**SparSP makes sparse attention useful to the communication system as well as the compute kernel.** It groups queries with overlapping dependencies, delivers selected key/value (KV) blocks directly to their consumers, and uses asynchronous peer copies and selective chunking to overlap data movement with attention.

## Why a Faster Kernel Can Leave GPUs Waiting

A video diffusion transformer processes a long sequence of visual tokens over repeated denoising steps. Sequence parallelism distributes that sequence across GPUs: each GPU owns part of the queries but may need keys and values stored elsewhere to compute attention. A GPU computes against one shard while another shard is in flight. This works well when computation is long enough to cover the transfer.

Sparse attention changes that balance. Computational savings exceed communication savings, even under an optimistic exchange that sends each rank only the blocks it needs with the original placement. Less computation also means less time to hide communication.

Why does so much data still move? A GPU needs the **union of the KV blocks requested by all its local queries**. Each query can be sparse while that union is large.

For a small illustrative example, suppose one query needs blocks `{A, B}` and another needs `{C, D}`. Placing them together makes their GPU request four distinct blocks. Pairing queries that both need `{A, B}` instead reduces the communication demand. The individual attention masks need not change for placement to change the communication cost.

Two additional problems remain after reducing this union. A conventional ring can forward blocks through GPUs that never use them, and the remaining transfers can still stall attention or compete with it for GPU execution resources.

## Ask for KV Before Moving It

Before sending KV data, SparSP determines which blocks each GPU needs. A block is a group of tokens processed together by the sparse attention kernel. For each attention head, the kernel's mask records which KV blocks each query block will read.

The challenge is to build that mask without first transferring all the keys. SparSP uses the pooled Q and K summaries already required by the sparse attention backend. Each GPU exchanges its compact K summaries, combines the received summaries with its local Q summaries, and constructs the mask. These summaries are much smaller than the full K tensor; their exchange can overlap with value projection.

The receiver then collects the remote block IDs selected by its local queries. Suppose two query blocks on GPU 1 need blocks `{A, C}` and `{C, D}` from GPU 0 for the same head. GPU 1 requests `{A, C, D}`: it receives C once and reuses it for both queries. Blocks already on GPU 1 require no transfer.

Requests stay separate across heads. If head 0 needs A and head 1 needs D, the payload contains head 0's A and head 1's D. Sending both blocks for both heads would add data neither head requested.

Each GPU exchanges its request masks with its peers once per attention call. The sender now knows what to pack, and the receiver knows what to expect. Both enumerate the selected blocks in the same order, first by head and then by block ID. They can therefore calculate each head's byte range locally, without sending a separate list of offsets with every payload. Placement is reused across calls, but these requests are rebuilt from the current attention mask.

## Make Placement Follow Shared Dependencies

SparSP starts with a property of video attention: queries at corresponding spatial regions in different frames often attend to overlapping KV regions. Contiguous partitioning of the flattened video sequence does not necessarily keep those queries together.

<p align="center">
  <a href="/assets/figures/sparsp/attention-patterns.png"><img src="/assets/figures/sparsp/attention-patterns.png" alt="Multi-diagonal attention patterns dominate the sparse heads in the evaluated video models." width="100%"></a>
</p>

*Dominant multi-diagonal structure connects corresponding regions across frames, motivating a placement that repeats at frame boundaries.*

SparSP assigns the same spatial interval to the same GPU in every frame. Consider four GPUs and eight blocks per frame: GPU 0 owns blocks 0-1 from every frame, GPU 1 owns blocks 2-3, GPU 2 owns blocks 4-5, and GPU 3 owns blocks 6-7. Each GPU still receives an equal share of the blocks, but its share now spans all frames.

If a query at block 2 attends to block 2 in other frames, those accesses stay on GPU 1. Nearby queries can also share the same remote blocks: queries near an interval boundary may request neighboring blocks from another GPU, which are transferred once per receiving head and reused locally. With contiguous sequence partitioning, corresponding regions in different frames can land on different GPUs, requiring repeated remote fetches.

<p align="center">
  <a href="/assets/figures/sparsp/placement.png"><img src="/assets/figures/sparsp/placement.png" alt="The paper's placement example reduces transferred blocks from 23 to 16 by regrouping queries and keys with overlapping dependencies." width="100%"></a>
</p>

*In this illustrative example from the paper, changing placement reduces transfers from 23 blocks to 16 while preserving the attention mask. This is an example of the mechanism, not an aggregate benchmark result.*

This placement follows the model's recurring attention patterns. It does not require knowing every layer's exact mask in advance. SparSP computes the block permutation for a given model geometry and GPU count, then reuses it across layers and denoising steps.

The permutation moves whole blocks without changing which tokens belong to each block. Hidden states and their position information, including rotary positional embeddings (RoPE), follow the same mapping. A token retains its original position even when it moves to another GPU. After the distributed computation, the inverse permutation restores the original sequence order.

This preserves the selected query-KV relationships under the corresponding index mapping. It does not guarantee bitwise-identical outputs: changing the order in which online softmax combines partial results can introduce small floating-point rounding differences.

## Deliver Blocks Directly to Their Consumers

Suppose GPU 0 owns blocks A through D. GPU 1 needs A, GPU 2 needs B and C, and GPU 3 needs D. In a conventional ring, GPU 0 first sends ABCD to GPU 1. GPU 1 uses A but must forward BCD to GPU 2, which uses BC and forwards D to GPU 3. D crosses three GPU-to-GPU transfers even though only GPU 3 consumes it.

SparSP changes the peer in each round. For GPU 0, the first remote exchange delivers A to GPU 1, the next delivers BC directly to GPU 2, and the last delivers D directly to GPU 3. Other GPUs follow the same rotating-peer schedule for the blocks they own. Each payload contains only the blocks requested by that round's receiver.

In this example, the relay sends eight block copies in total: four, then three, then one. Direct delivery sends four: one, then two, then one. These counts illustrate the routing difference, not a measured speedup. A block requested by several GPUs still needs a copy at each consumer.

The attention computation continues to process available KV blocks in stages, accumulating partial results with online softmax. What changes is where the next payload comes from: its original owner supplies it directly, instead of an intermediate GPU forwarding it.

Direct delivery is a logical routing decision. It does not remove PCIe switches, host bridges, or inter-socket links from the physical path. That distinction matters: in the paper's A100 and L40S experiments, direct routing alone may hurt performance by adding cross-NUMA traffic. Combining it with dependency-aware placement reduces demand enough to produce a net benefit. On the evaluated single-NUMA platform, direct routing consistently reduces latency.

## Let Transfers Progress Alongside Attention

The selected blocks still need to reach the receiver while attention is running. In the evaluated baseline, communication kernels share streaming multiprocessors (SMs) with attention kernels. SparSP uses the GPU's DMA copy engines for bulk peer transfers, leaving SMs available for computation. Packing and scattering still use GPU kernels, and transfers still consume memory and PCIe bandwidth.

The runtime uses a small set of reusable buffers called slots. Before execution, each GPU shares CUDA IPC memory handles so its peers can access these slots. This is the **Export** operation in the figure. The buffers remain in place across attention calls unless the execution configuration changes.

Consider GPU 0 preparing data for GPU 1. GPU 0 gathers the requested K and V blocks into a free slot. GPU 1 already knows their order from the exchanged request mask, so it can derive the byte range to copy from that slot.

**Publish makes the payload safe to read.** GPU 0 sends a one-byte NCCL notification after packing. The notification is issued on the same CUDA stream as the pack operation, so it cannot overtake the writes that prepare the payload.

**Fetch copies the payload to the receiver.** Once notified, GPU 1 issues an asynchronous peer copy through DMA. After the copy completes, a scatter kernel puts the received blocks into the layout expected by sparse attention. Attention can then consume them; it must not read a block while that block is still arriving.

**Release makes the source slot safe to reuse.** After the copy finishes, the receiver writes a four-byte completion value to shared state. The producer checks that state before overwriting the source slot. The receiver now has its own copy, so subsequent local computation does not require keeping the producer's slot occupied.

Multiple slots let the producer prepare another payload while an earlier slot remains in use. This avoids a global barrier after every transfer. A separate **Fence**, implemented with an NCCL barrier at the start of an attention call, ensures that the previous call has finished before the slot state is reset. NCCL handles these small control operations; DMA carries the bulk KV data.

### Shorten the Final Wait

With a whole-payload transfer, the receiver waits for all selected KV data from a peer before starting the corresponding attention work. This is especially costly for the last peer: after that transfer finishes, the remaining computation adds directly to completion time.

SparSP splits remote payloads into groups of attention heads. For example, with two chunks, it can copy and scatter the first group's selected KV blocks, start attention for that group, and transfer the second group while the first computes. Each group starts only after its own data is ready.

The local shard stays intact because it needs no transfer. Earlier remote exchanges already overlap with later transfers, so splitting them too finely often adds more launch overhead than it saves. SparSP tunes their chunk count separately from the final exchange, where an earlier start can shorten the pipeline drain. It also schedules the sparsest head group last, reducing the computation left after the final copy.

More chunks are not always better. Kernel launches and scheduling add overhead. The paper finds no tail-chunking benefit for HunyuanVideo, whose smaller head count leaves less room for useful subdivision.

## Ablation: What Each Component Contributes

SparSP is implemented in approximately 2,500 lines of Python and C++/CUDA on Diffusers. The ablation uses SpargeAttn in CDF mode, with default thresholds of 0.85 for LTX-Video, 0.90 for LTX-2, and 0.85 for HunyuanVideo.

The three platforms are:

| Platform | GPU memory | Evaluated interconnect and topology |
| --- | --- | --- |
| 8 A100 SXM4 GPUs | 40 GB per GPU | PCIe 4.0 x16; four GPUs per CPU socket; no NVLink connectivity in the evaluated configuration |
| 8 L40S GPUs | 48 GB per GPU | PCIe 4.0 x16; the same two-socket GPU grouping |
| 4 RTX 6000 PRO GPUs | 96 GB per GPU | PCIe 5.0; a single NUMA node |

Across these experimental platforms, **the off-diagonal GPU-to-GPU entries in `nvidia-smi topo -m` are exclusively `NODE` or `SYS`, and GPU peer-to-peer access is supported and permitted**. The diagonal `X` entries denote each GPU itself. There are no GPU-pair entries labeled `PIX`, `PXB`, `PHB`, or `NV#` in these configurations.

`NODE` describes a path through PCIe and the interconnect between PCIe host bridges within one NUMA node; `SYS` additionally crosses the interconnect between NUMA nodes. These labels describe the physical path, while P2P capability determines whether a GPU can access a peer's memory. A `NODE` or `SYS` path can therefore support P2P, as it does in our experiments. See NVIDIA's [topology documentation](https://docs.nvidia.com/deploy/nvidia-smi/index.html#topology).

The workloads use VidProM prompts and vary video length. Default resolutions are 768 x 1536 for LTX-Video and LTX-2, and 768 x 1280 for HunyuanVideo. LTX-2's two stages are reported separately. We choose these resolutions so each frame's tokens divide into whole blocks. Blocks that straddle frame boundaries can weaken the locality exploited by frame-aware placement. Limited VRAM requires FP8 weight-only quantization for LTX-Video and LTX-2 on A100 and L40S, while activations remain in BF16. The communication savings therefore do not come from reduced activation precision.

### Engineering Detail: P2P Support and NCCL Transport Selection

**P2P being available on the server does not guarantee that NCCL's default policy will select it.** In the tested configuration, the conservative default cutoff described in the paper allows P2P only up to `PXB`. Our `NODE` and `SYS` GPU pairs lie beyond that cutoff, so NCCL falls back to host-backed shared-memory communication despite available GPU peer access. NCCL has no `NODE` setting for this variable, but that naming difference alone does not explain its default choice.

We explicitly set the following before launching the tuned Ring Attention baseline:

```bash
export NCCL_P2P_LEVEL=SYS
```

This expands NCCL's permitted P2P distance to include paths across NUMA nodes, allowing the supported peer-access paths in these servers to be used. It substantially improves Ring Attention's point-to-point bandwidth. The setting controls transport eligibility; it does not change the physical topology or create P2P support on a machine that lacks it. Also, `NODE` is a label in the `nvidia-smi` topology matrix, not a value to substitute into `NCCL_P2P_LEVEL`.

*Higher is better. All configurations in this ablation already use demand-directed routing. The bars show successive additions relative to naive placement; they do not isolate routing's contribution.*

Read the bars as a sequence of additions: naive placement, dependency-aware placement, the decoupled runtime, and adaptive chunking. The decoupled runtime contributes the largest improvement in this ablation. Placement helps reduce demand, while chunking provides a smaller, workload-dependent benefit.

HunyuanVideo illustrates why these components need separate evaluation: placement benefits from its sparse dependencies, but the final chunking addition provides no meaningful gain because the smaller head count limits useful subdivision. For the other workloads, chunking can shorten the exposed drain. The components address different sources of cost, so their gains should not be multiplied as independent speedups. Because routing is enabled in every bar, this figure measures the additions on top of direct routing rather than isolating routing itself.

## What This Means for Inference Engine Design

SparSP makes the sparse dependency graph useful beyond the attention kernel. The same information guides which queries share a GPU, which KV blocks move between peers, and when a consumer can start work.

For inference-engine developers, three implications follow from the results:

- **Measure demand after partitioning.** Per-query sparsity can overstate communication savings when local queries request largely disjoint blocks.
- **Evaluate placement and routing together.** Fewer logical transfers do not guarantee lower latency when the physical topology changes their cost.
- **Tune overlap around the remaining work.** Faster attention reduces the time available to hide communication, while overly fine chunking adds overhead.

As attention kernels become faster, communication increasingly determines whether their gains survive multi-GPU execution. SparSP shows how coordinating placement, routing, and transfer scheduling can turn those kernel improvements into lower denoising latency.
